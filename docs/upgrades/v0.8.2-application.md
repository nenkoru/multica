## Private-project boundaries

Existing projects migrate to workspace visibility, so their custom features
retain their previous behavior. New private projects introduce these rules:

- Planning reads use the upstream member/agent-run principal policy. Counts,
  progress, attention, activity and burndown exclude hidden issues before
  aggregation, sorting and limiting. Ordinary issue filters keep this policy.
- Planning writes require visibility of all workspace projects. Relation
  deletion and sprint completion otherwise mutate issues the caller cannot see.
  A partial planning mutation returns 403 before changing anything.
- Fabrika prose summaries, journal entries and generated screens cannot be
  reconstructed as partial views. All member Fabrika routes return 404 for a
  caller with hidden projects. Owners/admins and principals who can see every
  private project keep access. The health probe remains timestamp-only.
- A kiosk token represents a workspace, without human project principals.
  TV overview, game and health return 404 in a workspace containing private
  projects. The realtime kiosk projection remains a content-free change signal.
- Multika's daemon claim checks the current run's originator (or accountable
  fallback) and agent owner before reading streams, replaying turn actions,
  changing shared focus, answering asks or building screens. The task must
  belong to that agent, workspace and chat session. Hidden projects or access
  lookup failures yield a generic denial without Fabrika actions. Charter
  replies and final screen delivery recheck access, including revocations
  after the claim. This also covers the non-HTTP hooks identified in RUSL-2938.

These conservative limits are deliberate. Do not remove the guards without
complete project-aware projections and matching authorization tests. They do
not grant Connected Apps accounts, expand agent mandates or change task roles.

## Delivery and rollback gates

Do not run the old hard-coded `rollout-rusl2760.sh` against this candidate.
Before any rollout, the fork custodian must stage new artifacts and update the
release manifest, exact hashes, readiness checks and rollback baseline to the
accepted v0.8.1 installation. Preserve independent DSH review and Mika acceptance.

At rollout time take a fresh production dump, verify restoration, then rehearse
candidate migrations on that restored copy and compare actual planning/Fabrika
counts. Synthetic rehearsal does not replace that gate. Retain old image
digests and both daemon binaries; drain atomically and deploy server/migrations/
frontend, primary daemon/CLI, then standby. Check a complete short agent run,
issue create/update/comment, chat reads and autopilots; observe for 30 minutes.
The separate original openui visual acceptance remains outstanding.

Before deployment, rollback is closing the application PR; no running service
changes. After deployment, drain again, restore saved v0.8.1 images and primary
binary, verify exact version and maintenance readiness, resume, then restore
standby. If schema rollback is necessary, preserve new data and restore the
verified dump in a quiescent window; never automatically run destructive down
migrations after writes resume.
