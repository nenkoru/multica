# Multica v0.8.2: оценка обновления self-host форка

RUSL-2897, 11 ноября 2026 года, 15:06 МСК. Результат — план переноса,
а не готовая сборка. Рекомендуется обновление до закреплённого `v0.8.2`
после интеграции custom-слоя, кластерных проверок и ревью DSH.
Недоступность buvg01 оценке и CPU-сборкам не мешает.

на «не запущен / проверки отсутствуют». Ожидать завершения несуществующего run
не нужно.

В [CI на закреплённой базе](https://github.com/nenkoru/multica/blob/44882282ffc9df552677ba563e7290e719ba8db2/.github/workflows/ci.yml)

Базы перечисленных PR под фильтр не попадают. Исторические runs другого PR

их чтение имеющимся токеном получило HTTP 403; дополнительных прав не запрашивали.

До application merge нужны проверки точной интеграции через `kjob` и DSH.
Для слияния в `main` отдельно сохраняется требование зелёного GitHub CI:
нельзя подменять его `CLEAN` или прошлым кластерным прогоном. Публикация во
`fabrika` сама по себе Actions CI не запускает. Изменение workflows в этот PR
не входит; существующее ограничение workflow scope отмечено в FORK.md PR #22.

## Изменения контрактов и риски совместимости

1. **Приватные проекты теперь доступны всем.** Миграции 630–632 сохраняют
   существующим проектам `visibility=workspace`, но новые private-проекты
   фильтруются по участникам и principals запуска. В upstream проверка проходит
   через `projectaccess`, `project_access.go`, выдачу задач, поиск, комментарии,
   вложения и чат. Наши planning/TV/Fabrika endpoints автоматически такую
   проверку не получают: при переносе проверить все места выдачи project issues,
   счётчиков и артефактов, включая agent-owner и triggered-by.
   [Код доступа](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/internal/handler/project_access.go).
2. **Connected Apps меняет модель доступа.** Появляются team/personal accounts,
   agent apps, правила действий, подтверждения и журнал вызовов. Миграция 617
   переносит прежние allowlists как `personal` + `confirm_writes`. Сохранить
   upstream-проверки; сопоставить их с Fabrika mandate/ask, не превращать наличие
   мандата в обход подтверждений Connected Apps. Подключать новые аккаунты для
   проверки переноса не требуется.
   [Миграция 617](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/migrations/617_connected_apps.up.sql).
3. **Вложения LocalStorage требуют авторизованной загрузки.** Legacy `/uploads`
   entry закрыт для произвольного публичного чтения; bound attachments получают
   стабильный API URL, `cdn_signed=true` используется также для LocalStorage.
   Bare `<img src>` с token-mode URL может перестать работать. Проверить старые
   Markdown-ссылки, UI-block screens, voice/audio/PDF и CLI download через
   существующие авторизованные endpoints. Не возвращать публичную раздачу.
   [Преобразование URL](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/internal/handler/file.go),
   [тест совместимости](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/internal/handler/file_local_compat_test.go).
4. **Daemon start проверяет именно запущенный child.** Upstream больше не
   сообщает успех после timeout без совпавших PID/profile/health. Новый dev-env
   режим допускает управление только собственным профилем среды. Сохранить
   границу task/operator в custom maintenance; не использовать dev-env для
   управления production-демоном. Операционные скрипты должны проверять новую
   версию и readiness. Новые environment snapshots и Muse cleanup capability
   поддерживают порядок «сервер перед демоном»; Muse не включать ради обновления.
   [CLI daemon](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/cmd/multica/cmd_daemon.go),
   [daemon client](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/internal/daemon/client.go).
5. **CLI меняется в общих файлах.** Добавлены `issue search --project`, управление
   PR auto-complete и status icons; исправлена привязка comment attachments.
   При переносе planning-флагов и chat-команд сохранить upstream argv/attachment
   исправления. Codex получил промежуточный вывод текста; это не заменяет нашу
   attribution/masking логику. Общего принудительного разрыва всех старых
   клиентов статическим просмотром не установлено; совместимость смешанных
   версий ещё требует проверки.
   [CLI issue](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/cmd/multica/cmd_issue.go),
   [Codex](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/server/pkg/agent/codex.go).
6. **Frontend и сборка.** Добавлены русский locale, Appearance и изменён Work
   panel. Нашим planning/streams namespaces нужны русские переводы и parity.
   Ужесточены package boundaries, dependency catalog и accessibility lint:
   проверить custom imports и icon-only кнопки. Web больше не использует
   `next build --webpack`, Fumadocs перешёл на общий catalog. Go остаётся 1.26.9,
   Node >=22, pnpm 10.28.2; `server/go.mod`/`go.sum` между тегами не менялись.
   Проверить реальную frontend image build в kjob.
   [Package scripts](https://github.com/multica-ai/multica/blob/b7f8efcaae6c5f3273c0038252b5d10c81b41068/apps/web/package.json).

## Миграции

Добавлено **20 up/down-пар: 617–636**, существующие upstream-миграции
в этом диапазоне обновления не изменены и не удалены.

| Номера | Что меняют | Что проверить |
| --- | --- | --- |
| 617 | 7 таблиц Connected Apps и backfill allowlist → agent_app | Перенос allowlists, уровни и scope, отсутствие дубликатов |
| 618–628 | 11 concurrent indexes Connected Apps | Unique keys, cleanup invalid indexes, повтор после прерывания |
| 629 | 3 поля GitHub star prompt у user | Defaults, сохранность user rows |
| 630 | project.visibility, default workspace | Существующие проекты остаются доступны |
| 631–632 | project_member и concurrent user index | Membership, teardown, запреты доступа |
| 633–635 | issue_environment и 2 concurrent indexes | Snapshot/report lifecycle, cleanup |
| 636 | site_counter | Manifest классифицирует global rows как keep |

Всего 14 concurrent index builds. Upstream регистрирует их cleanup в
`server/cmd/migrate/main.go`; сохранить нашу запись
`9005_fabrika_ui_block_session_idx → idx_ui_block_session`. PR #23 уже содержит
оба исправления PR #19: cleanup 9005 и 13 `fabrika-external` записей manifest.
При переносе использовать фактический diff, не дублировать их слепым cherry-pick.
Upstream добавляет manifest для новых таблиц; конфликт нужно объединить с нашими
записями. Классификация `fabrika-external` по-прежнему не реализует удаление данных
Fabrika при удалении workspace — это известный отдельный пробел.

В v0.8.1 upstream 640 up-файлов, в custom PR #23 — 658, в v0.8.2 upstream —
660. При сохранении всех 18 custom migrations ожидается **678 up-файлов**
в кандидате. Это число файлов, не измеренное состояние production БД.
Custom prefixes 565–576 и 9000–9005 не пересекаются с новыми 617–636;
исторические дубли префиксов учитываются runner по полному имени файла.

Все новые up SQL просмотрены статически; они добавляют схему и backfill,
down удаляет новые таблицы, индексы или колонки и может потерять новые данные.
Перед установкой обязательны свежий `pg_dump`, восстановление в пустую БД,
переход восстановленной custom-базы к кандидату, проверка full migration names,
валидности индексов и контрольных счётчиков planning/Fabrika.
В этом шаге SQL не выполнялся. Автоматический down после возобновления записей
не является планом отката.

## Порядок реализации в следующем application PR

1. Начать integration branch от закреплённого `v0.8.2`. Источник custom-слоя —
   закреплённый PR #23, включая приложение #22. Сопоставить с принятым
   integration bundle RUSL-2760 и установленными build refs; GitHub publication
   history отличается из-за сохранения workflows. Не сливать устаревшую
   `fabrika` как полный источник приложения.
2. Перенести только custom delta относительно v0.8.1 с сохранением upstream
   изменений. Не копировать целиком daemon.go, issue.go, schemas или generated DB
   поверх v0.8.2. Generated sqlc и reserved-slugs пересобрать после согласования
   source SQL/JSON. Work-panel links planning/streams оставить в новой структуре.
3. Разрешить текстовые конфликты, затем проверить семантику доступа, lifecycle,
   redaction, locale и вложений даже в автоматически объединённых файлах.
   Предварительный `merge-tree` с явной базой v0.8.1 выявил **17 конфликтных
   путей**: core api/diagnostics/reserved-slugs, issue-detail, 7 issues locales,
   handler issue/reserved-slugs/workspace-delete manifest, query issue и
   generated issue/models. Полный список в evidence. Это проба объединения
   снимков, не готовая интеграция и не результат тестов.
4. В `kjob` nenkoru-prod или ru-exec собрать server, CLI и frontend. Проверить
   Go race для daemon/maintenance/redact/agent, CLI и DB-backed handler/service/
   migrations. На восстановленной БД проверить cleanup всех concurrent builds,
   workspace deletion manifest и новые private project cases для custom paths.
   Для frontend — typecheck/lint, locale parity, planning/streams/chat,
   virtualizer, UI blocks, auth media и штатную image build. Запусков на buvg01
   и аренды GPU для этих проверок не нужно.
5. Перенести и актуализировать maintenance operations tests, negative traps и
   restore/readiness проверки с baseline v0.8.1. Опубликовать application PR
   в форк с точным SHA и квитанциями kjob. Если workflow-scope всё ещё ограничен,
   сохранить существующий publication pattern и bundle integration history;
   не заявлять GitHub CI зелёным без check runs. Ревью — Ревьюер (DSH), приёмка — Mika.
6. После проверок выполнить процедуру RUSL-2508: fresh dump + restore rehearsal,
   старые v0.8.1 images/digests и оба бинарника `*-bak`, durable unit вне cgroup
   демона, atomic drain claims/tasks/reports. Порядок: сервер/миграции/frontend
   → primary daemon/CLI → standby. Проверить version, issue create/update/comment,
   короткий agent run, чтение чата Mika, автопилоты и 30 минут наблюдения.
   Исходная визуальная приёмка openui RUSL-2773/2802 остаётся отдельной проверкой.

## Проверено и откат

Выполнены: чтение stable release и тегов, полный git diff, просмотр новых
up/down SQL, сравнение custom paths, трёхсторонняя merge-tree проба без изменения
рабочей application tree и read-only проверки PR/checks/runs. Для этой документации
проверяются `git diff --check`, JSON и ссылки на закреплённые refs.
Сборки, runtime tests, восстановление БД и выкатка в этом шаге не выполнялись.

Откат этого PR — revert документирующего коммита. Откат будущей установки:
atomic drain → сохранённые v0.8.1 backend/frontend с readiness → старый primary
с maintenance → readiness/resume → standby. При необходимости вернуть схему —
использовать проверенный дамп в окне без записей с отдельным сохранением новых
данных; destructive down автоматически не выполнять. Production, сеть,
сертификаты, доступы и runtime/model агентов этим PR не меняются.
